# Как писать DKT-код: намерение, граф и проверяемые гарантии

Дата: 2026-09-07. Дополнение к `main-ru.md` и DKT `docs/overview.md` по результатам миграции MiniCut и проверки Define Ambition. Примеры описывают принципы; точный синтаксис следует сверять с contract-тестами используемого DKT SHA.

## Основная идея

Пиши код так, чтобы DKT мог определить, какие данные нужны операции, какое изменение она выражает и какие связи обязан сохранить. Прикладная функция вычисляет результат по переданным данным; декларации описывают чтение, запись, ownership и переход к side effects.

Это даёт фреймворку свободу менять способ исполнения: подгружать данные, пересчитывать зависимости, сохранять граф, передавать изменения между контекстами и ограничивать доставку запрошенным подграфом. Такие возможности требуют соответствующей настройки runtime и схемы; одна декларативность не гарантирует их автоматически.

Если функция тайно читает модель через object API, сама обходит registry или запускает следующую фазу из callback, существенная часть намерения становится невидимой. Локально код может работать, но его корректность начинает зависеть от полной загрузки графа, порядка callbacks или конкретного процесса исполнения.

Практический критерий: сможет ли эта операция корректно работать, если нужные данные придётся подгрузить, owner придёт с другой реплики, а UI получит только запрошенную часть графа?

## Что показала миграция

| Проблема MiniCut | Что выяснилось по истории и тестам DKT | Урок для нового кода |
| --- | --- | --- |
| Создание через root collections и legacy model-rel | Registry типов отделён от relations экземпляров; constructor должен разрешаться через schema, создание — через owner | Сначала определить owner и допустимый target, затем писать action |
| Ручные child → owner записи | DKT поддерживает inverse и отвергает независимые app writes в mirror | Одна связь должна иметь одну каноническую сторону изменения |
| Multi ownership при одиночной обратной relation | Новая validation обнаружила противоречие между cardinality и выбранной моделью владения | Выбирать cardinality по предметной области, а не ради прохождения validation |
| Вложенный `use_ref_id` в creation payload | Ссылка action frame смешивалась с данными создаваемой модели | Передавать промежуточные результаты на предусмотренной границе фаз |
| `rels.sel` и зависимость от root projections | Selection переехала в computed relation с адресными dependencies; projection не обязана быть полным глобальным индексом | Объявлять запрос и путь к данным вместо сканирования имеющихся экземпляров |
| Старый SessionRoot bootstrap | Создание session root стало явным framework bootstrap с `{ rel, attrs }` | Отделять модель внимания пользователя от domain ownership |
| Promise-вызовы raw graph storage | Конкретный graph storage API стал callback-first requestor; другие storage API сохранили свои контракты | Проверять контракт конкретной границы, не унифицировать похожие API на глаз |
| Обновление storage manifest | V2 меняет физические ключи, dictionary и кодирование значений | Мигрировать представление данных атомарно с метаданными формата |
| Receiver без prune chunk `7` | Удаление replica — упорядоченная часть update stream; fields доставляются по активным shapes | Проверять удаление и изменение подписок вместе с обычными updates |
| Создание child у incoming owner без `app` | Runtime материализует owner с `_highway`, но `initSi` не передавал этот runtime дальше | После восстановления проверять способность продолжить работу, а не только читать snapshot |

История июня 2026 показывает связанный переход: refs, registry, inverse и ownership validation, write boundaries, SessionRoot, selections, prune, storage v2 и shape delivery. Массовая синтаксическая замена не могла завершить эту миграцию: часть ошибок требовала выбрать правильную предметную модель.

## Правила принятия решений

### 1. Начинай с инварианта, затем выбирай декларацию

До реализации опиши, что обязано оставаться истинным: кто владеет объектом, какие связи допустимы, что означает завершённая операция. Например: «clip принадлежит track; удаление из пользовательской выборки не обязательно удаляет clip из domain graph».

Не выбирай owner по тому, из какого компонента удобнее вызвать creation. Owner отвечает за lifecycle, а selection и navigation — за доступ и внимание. Эти роли могут принадлежать разным моделям.

Проверь отдельно создание, изменение связи и удаление. Успешное создание ещё не доказывает правильность ownership.

### 2. Разделяй исходное состояние, вычисление и внешний ресурс

Сохраняемый факт описывай input attr/rel. Значение, однозначно выводимое из графа, выражай через comp. Внешнюю операцию запускай через effects/runtime boundary.

Не поддерживай вручную `active`, `latest` или итоговый counter, если это полностью производная функция существующего состояния. Такая копия требует собственного протокола согласования при каждом изменении, reinit и sync.

Исторический факт или зафиксированный snapshot может быть самостоятельным состоянием, даже если при создании вычислен из других данных. Критерий — смысл значения, а не возможность вычислить его один раз.

### 3. Передавай функции нужные данные через declared dependencies

Model ref в прикладной логике используй как identity/scope. Если reducer нужен `status`, объяви чтение `status`. Если нужны attrs моделей по цепочке relations, вырази путь в dependency.

Не прячь чтение в helper, который принимает модель и вызывает `getAttr`, просматривает внутренние attrs или обходит runtime registry. DKT должен видеть и конечное поле, и связи, изменение которых меняет результат запроса.

Pure helper допустим: он получает значения и вычисляет результат. Технические storage/sync adapters и diagnostic readers имеют другую роль; их низкоуровневые операции не являются образцом для domain actions.

### 4. Храни отношения как relations и меняй каноническую сторону

Внутреннюю связь между моделями выражай rel, а не attr с ID и последующим join. На внешней границе ID нормален; преобразуй его в scope/ref предусмотренным механизмом адресации.

Создавай через owner-rel. Если inverse объявлен управляемым DKT, не записывай его вручную. Registry отвечает за доступные типы, projection — за выборку, owner — за lifecycle.

Не запрещай `can_create: true` само по себе: на однозначной modern owner relation эта форма валидна. Проверяй разрешимость constructor и authority target.

### 5. Выражай пользовательскую операцию настолько точно, насколько позволяет API

Добавление, удаление, перенос и полная замена списка имеют разный смысл. Выбирай relation method, который соответствует операции, особенно для collaborative state.

Не превращай каждый edit в чтение массива и запись новой полной копии. Так теряются сведения о намерении и anchor операции, полезные для обработки конкурентных изменений.

Полная замена допустима, когда именно она является намерением: например, импорт целого списка. Semantic method помогает DKT интерпретировать операцию, но сам по себе не решает все конфликты.

### 6. Описывай порядок фаз внутри workflow

Зависимые изменения выражай через action phases, declared targets, `$output` и `sub_flow` согласно контракту текущей версии. Промежуточную ссылку передавай как результат фазы, а не как marker, спрятанный внутри creation data.

Не строй domain workflow как внешний `dispatch → прочитать состояние → dispatch`. У такого координатора появляются собственные правила порядка, завершения и восстановления.

Не считай любую saga одной атомарной транзакцией автоматически. Установи конкретную границу commit и отдельно поведение на внешнем I/O. Между request и completion могли измениться owner, selection или актуальность операции.

### 7. Держи side effects на явной границе

Action формирует намерение и данные запроса. Boundary работает с сетью, файлами, временем, worker или media API. Результат возвращается явным событием/action с идентификатором операции и необходимыми данными.

Не переноси в boundary решения о том, какой domain object активен и какую relation надо изменить. Не считывай глобальные часы внутри pure reducer/comp; время должно быть объявленной dependency или входными данными события.

Храни в графе serializable metadata/status/refs. `File`, `MessagePort` и другие live objects требуют runtime boundary. Object URL тоже привязан к runtime lifetime, хотя технически является строкой.

### 8. Считай частичность графа штатным условием

Наличие ref не доказывает, что все attrs загружены. Отсутствие поля в renderer не доказывает, что domain state отсутствует. Недоставленная projection не является полным индексом моделей.

Объявляй данные, нужные UI, через scopes и shapes. Domain selection помещай в comp rel; per-model derived values — в comp attrs. Компонент управляет представлением и явно необходимым сроком подписки.

Не исправляй отсутствующие данные fallback-ом к debug dump или global replica scan. Проверь последовательно model schema, dependency/query, shape request, delivery и receiver lifecycle.

### 9. Рассматривай восстановление как ещё один вход в рабочий lifecycle

Объект может появиться после local creation, incoming batch или storage reinit. Не предполагай, что все пути повторяют обычный constructor/bootstrap приложения.

В runtime-коде используй уже известный runtime напрямую; не восстанавливай его через необязательную graph-ссылку. В приложении пользуйся declarative contracts, не выставляй `_highway` или `app` вручную.

Проверяй последовательность: восстановили → прочитали → выполнили следующий action → передали/сохранили результат. Для UI replica отдельно проверяй prune и повторное получение нужного подграфа.

### 10. Тестируй границу гарантии и проверяй, что тест способен опровергнуть код

Для schema invariant нужен contract test с допустимым и запрещённым случаем. Для workflow — настоящие actions. Для sync/storage — прохождение соответствующей границы. Чтение assertions выполняй после write step в предусмотренном read flow.

Mock уместен для внешнего сервиса, но не должен подменять тот runtime механизм, корректность которого проверяется. Отдельный unit test локализует причину; integration test проверяет связь подсистем.

В PR #207 unit test и incoming-materialization integration test падают без `_highway: runtime`. Двухрепличный transport test после полного восстановления owner проходит и без этой строки: он проверяет соседний рабочий сценарий, но сам по себе не воспроизводит дефект. Эти роли тестов нужно различать.

Не лечи ошибку completion произвольным delay. Определи, какое событие или завершённая фаза гарантирует доступность результата. Зелёный тест должен подтверждать контракт, а не удачный порядок выполнения.

## Рабочая стратегия для новой возможности

1. Запиши предметный инвариант и пользовательское намерение.
2. Разложи данные на input state, derived state, session state и runtime resources.
3. Определи owners, refs, inverse и cardinality.
4. Объяви чтения, targets и передачу результатов между зависимыми фазами.
5. Отдельно обозначь I/O и условия принятия его результата.
6. Проверь сценарий при частично загруженном графе, после receive/reinit и при удалении, если эти пути затронуты.
7. Если DKT отвергает конструкцию, установи нарушенный инвариант по реализации и тестам; если ошибается framework, сделай минимальный framework regression.

Изменение хорошо выражено, когда его предметный смысл остаётся тем же при другом размещении runtime, другом порядке загрузки данных и другом способе доставки updates в рамках поддерживаемых контрактов.
